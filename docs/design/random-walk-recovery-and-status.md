# 随机漫步：后台恢复与关联准备状态

Status: Implementing — 2026-10-28。Evan 已明确要求执行修复，并在修复版写入新的用量数据前清空旧账本，方便比较。以下设计随实现与验证完善。

关联需求：[#38](https://github.com/EgoSay/kairos/issues/38)。依据：`BRAND.md`、当前 `1.8.0 / efb559de73cc` 源码、2026-10-28 14:55（北京时间）的只读生产快照和隔离复现。既有 A+C 设计已冻结，本文件只设计后续可靠性与可追踪性修复。

## 1. 产品目标与事实边界

让本人放心继续阅读：后台能恢复的问题自行恢复；暂时无法完成时，能知道发生了什么、什么时候继续、是否需要自己做事。关联准备失败不能被表述为原文保存或消息同步失败。

用户无需管理队列、选择待分析标签、每天点一次重试，或为了看到原文先处理警告。保持 A+C 的连续原文与可选地图。原文和真实引文优先于“让成功率好看”。

上一轮快照为：737 条来源，已准备 47、失败 17、等应用预算 666、已排除 7；派生关系 107 条。17 条失败原文都在，但历史详细原因未保存，不能追认成“网络错误”或“模型输出错误”。这些是带时间的诊断数据，不是本方案的新实时查询结果。

本轮设计覆盖：错误分类、自动恢复、用量结算、状态统计、进度明细、有限人工重试、旧失败任务恢复及验证。沿用现有 Go、SQL 数据库和 Cloudflare 模型，不新增图数据库、消息队列、监控 SaaS 或付费依赖。每日应用预算继续为 8,000 Neurons，不自动换服务或升级付费。

成功信号：用户可以解释“记录有没有保存”“这条为什么尚未准备好”“接下来会怎样”；工程上能够定位具体失败阶段，证明等待不消耗失败次数、重试不绕过预算、不重复结算、不发表无依据的关系。整体图谱质量与全库完成时间仍需真实运行观察。

## 2. 页面与信息层次

### 2.1 阅读页只留一句话

`/journal/wander` 继续先呈现原文。使用现有次级文字与 `quiet` 按钮，提供“查看进度”。后台状态加载或失败均不阻塞原文、提示展开、地图和返回。

| 情况 | 阅读页示例文案 |
| --- | --- |
| 正常回填 | 已准备 47 篇，更多关联正在后台整理。查看进度 |
| 预算不足 | 今天的关联准备先歇一歇，明天 08:00 起自动继续。查看进度 |
| 自动退避 | 关联服务暂时未响应，稍后会自动继续。查看进度 |
| 部分需要人工重启 | 有 3 篇暂未完成关联准备，已有原文和线索仍可阅读。查看进度 |
| 服务配置阻断 | 关联服务暂时不可用，需要检查连接。查看进度 |
| 全部完成 | 收起常驻状态句；设置中仍可打开“关联准备” |

多种情况同时发生时，主句说明当前整体阻断原因，明细完整保留其他状态；不能用“17 篇失败”盖住“666 篇等额度”。不弹出重复 Toast，不显示待办红点，不用环形完成率或虚构预计完成日期。时间使用用户时区，跨日显示日期；“08:00 起”是最早可恢复时间，不保证该时刻完成。

### 2.2 可选的“关联准备”面板

入口：阅读页“查看进度”，以及现有“关联准备设置”中的同名入口。建议使用 `/journal/wander?panel=preparation` 表达可直接打开的状态；不增加主导航栏目。

复用 `Sheet size="reading"`：桌面右侧抽屉、手机全宽底部面板，与“附近地图”一致。一次仅打开一个面板。关闭、Esc、浏览器返回只退出面板，保留原有阅读位置、起点、展开提示和地图返回栈；切换查询参数不重新抽取起点。

面板按以下顺序呈现：

1. 标题“关联准备”、最近更新时间。出现处理异常时注明“这里显示关联准备情况，不影响原文保存”。该句仅在服务器确认当前原文存在时使用。
2. 四个互斥计数：已准备、准备中、等额度、暂未完成。被本人排除的记录单独说明，不进入完成率分母。
3. 当前整体状态及下一步，例如“剩余额度不足下一次处理；10 月 29 日 08:00 起继续”。预算细节可展开，明确“本应用预算占用，含保守预留，不是 Cloudflare 账单”。
4. “暂未完成 / 准备中 / 已准备”筛选；准备中包含可进一步区分的排队、处理、自动重试与等额度。初次打开有异常则选“暂未完成”，否则选未完成部分。筛选变化不影响随机漫步选材。
5. 记录列表：日期和原文首句、停留阶段、易懂原因、最后尝试时间、下一步。真实原文按现行权限读取，不写入诊断日志。
6. 可选展开“处理详情”：最近尝试、准确错误类型、请求标识（如有）、预算结算状态。技术字段默认收起。

示意仅用于信息布局，数字取自上述历史快照，首句为虚构：

```text
关联准备                                      关闭
这里显示关联准备情况，不影响原文保存。

已准备 47   准备中 0   等额度 666   暂未完成 17
另有 7 篇不参与关联准备

剩余额度不足下一次处理，10 月 29 日 08:00 起继续。
本应用预算占用 7,992 / 8,000       预算说明 ▾

[暂未完成 17]  [准备中 666]  [已准备 47]
重新安排这 17 篇

10 月 20 日 · “今天终于把自己的需要说清楚……”
停在：寻找有关记录
历史版本未保存详细原因；再次处理后可查看完整结果。
最后尝试：未记录
查看原文       重新尝试       处理详情 ▾
```

“已准备”表示该轮语义处理完成，不保证找到关联。合法空结果显示“已检查，暂未发现可靠关联”，不计失败，也不为填满地图反复生成。

### 2.3 行为契约

| 操作 | 反馈与恢复 |
| --- | --- |
| 打开面板 | 先显示轻量外壳和已有汇总，明细按需加载；不等待模型；焦点进入面板标题或首个可操作控件 |
| 自动刷新 | 面板可见时每 15 秒刷新，隐藏时停止；阅读页沿用低频汇总。展示更新时间；新状态原位更新，当前展开项不突然消失或重新排序 |
| 单条重新尝试 | 立即进入提交中；服务端确认后显示“已加入后台准备”。预算不足则明确“已安排，额度恢复后继续”，不显示“处理成功” |
| 重新安排暂未完成项 | 一次操作，仅处理服务端确认可重试的异常项；不重新分析整库；反馈实际加入、已排队、跳过数量；普通可逆重排不再弹确认框 |
| 服务配置错误 | 说明需要更新连接，并提供既有 AI 设置入口；不让用户对每篇反复点击重试 |
| 查看原文 | 打开既有原文详情，返回时保留列表筛选与滚动位置；从未授权、删除或移出的记录不返回摘要 |
| 关闭面板 | 焦点回到触发入口；原文滚动位置保持不变；遵循 reduced-motion，触控目标至少 44px |

操作失败只在对应区域反馈。断网时保留带更新时间的已读状态，禁用会写入的重试操作；恢复后先核对状态，再恢复可操作性。退出账号立即清理私有缓存。屏幕阅读器仅播报用户操作结果和关键状态变化，不逐条播报轮询。

## 3. 后台状态与计数

把“是否允许运行 / 服务是否可用”与“某一条记录处理到哪里”拆开表达。汇总返回整体控制状态、各类计数和阻断原因数组，避免单个字符串互相覆盖。

| 任务状态 | 页面归类 | 含义 |
| --- | --- | --- |
| queued | 准备中 · 排队 | 当前版本等待领取 |
| processing | 准备中 · 正在处理 | 有未过期租约，显示当前阶段 |
| retry_wait | 准备中 · 等待自动重试 | 明确下一次尝试时间 |
| quota_wait | 等额度 | 应用请求预留不足，或 Cloudflare 明确返回日额度限制 |
| attention | 暂未完成 | 有限重试后仍未通过校验，或不适合自动重试的问题；可忽略，不影响原文 |
| ready | 已准备 | 当前版本处理完成，允许零条关系 |
| excluded | 不参与 | 不属于当前可处理集合 |

全局暂停或连接错误保留任务进度，面板统一解释为何暂时不运行；此时“准备中”计数文案改为“待继续”，不能制造“正在处理”的错觉。过期租约属于待恢复任务，不再计“正在处理”。

总量满足：参与数量 = 已准备 + 准备中 + 等额度 + 暂未完成。分类以同一快照的 owner、资格、当前 revision、profile、dirty 与有效租约共同判定，不能把仍为 `ready` 字符串但已 dirty 的旧结果计成完成。原有 `pending` 包含失败和预算等待，新 UI 使用新增互斥 `progress` 字段，不把旧 `pending` 当新口径。服务端维持旧接口兼容字段。

页面需与调度共用分类规则。汇总依据实际预留拒绝、任务等待和账号限制，不能只用 `used >= limit` 判断预算不足。若较小请求仍可执行，显示“部分记录等待额度”，让其他可执行任务继续；全部剩余可运行工作都受预算阻断时才显示整体等待。

## 4. 错误分类与恢复规则

提供带安全字段的类型化错误：阶段、错误码、HTTP 状态、供应商代码、请求标识、finish reason、Retry-After（存在才记录）。网络原因保留可判断的类型，不记录完整响应、原文、提示词、Token 或原始错误字符串中的私密信息。未知错误明确为 unknown/internal，不再归为 invalid-result。

下表时间与次数是本方案的首版建议参数，需以模拟时钟测试；不是从历史线上失败推导出的数值。

| 原因 | 自动处理 | 是否消耗结果失败次数 |
| --- | --- | --- |
| 应用预算不足 | 等下一预算日；同一天因确定用量结算释放足够余额时可重新调度 | 否 |
| 供应商明确日额度耗尽 | 账号级暂停至供应商规则对应的恢复时间；不能因本应用退款而提前解锁 | 否 |
| 网络、超时、408、429、5xx | 退避 1、5、30 分钟，其后低频 6 小时；优先遵守有效 Retry-After；带抖动 | 否；单独记录连续服务失败 |
| 返回被截断、JSON/结构错误、无效向量、引文不匹配 | 同一版本、同一阶段最多 3 次真实失败（首次 + 2 次重试，间隔 1、10 分钟），随后 attention | 是 |
| 401/403、无效端点、服务不可用配置 | 连接级暂停，设置页修复后恢复；不批量消耗每条记录的重试机会 | 否 |
| 其他 4xx、输入超限、索引容量限制 | 根据具体码区分请求约束/容量问题，给出准确原因；不一律称“配置错误”或循环重试 | 确定性限制直接 attention |
| 来源更新、排除、删除、权限变化 | 废弃迟到结果，按新版本重新排队或退出参与集合 | 否 |
| 进程关闭 / 主动取消 | 保留检查点，租约释放或到期后恢复；外部是否已消耗未知时保留预算预留 | 否 |
| 数据库或内部错误 | 独立错误分类，有限退避；三次连续无进展后 attention，并输出安全告警 | 单独计数，不伪装成模型失败 |

服务错误增加账号/连接级保护：连续三次服务不可用后短暂停止向同一连接发起工作，冷却 30 分钟，继续失败延长至 2 小时、6 小时；恢复时只放行一个正常待办请求作为探测，不额外发送私人测试文本。状态、冷却时间持久化，重启不清空。任意请求仍必须先通过预算门。401/403 等必须等连接配置实际变化，不以定时重复调用试密码。

领取任务不再增加失败次数。计数按“来源版本 + 阶段”保存，只在真实失败落库时增加；阶段成功后清零，领取、等额度和版本竞争都不消耗它。记录每次真实尝试时间，明确区分从未尝试、进行中、失败及未知历史时间。调度优先按到期时间，再按稳定 ID；重试回到队列，不能让低 ID 的坏任务长期挤占整库。

分阶段保留已验证结果：原文向量、关注点、关注点向量；已通过双方原文校验的关系如仅发布失败，可保存带双方版本的发布检查点。恢复前重新核验原文 hash、模型 profile、owner、资格和目标版本。只重做未完成或已失效的阶段。保留现有严格引文校验和合法空数组语义；首版不通过模糊匹配、放宽结构验证或强行连边来“修复失败”。

## 5. 用量与诊断持久化

继续以现有数据库为唯一事实来源，不引入通用工作流平台。

### 5.1 额度与计量口径修订（2026-10-28）

用户提供 Cloudflare 控制台 `1.69k / 10k` 截图后，本轮重新核对了[官方额度与模型费率](https://developers.cloudflare.com/workers-ai/platform/pricing/)及当前生产。官方每日免费额度是 **10,000 Neurons**；**8,000 是当前应用自设预算**，代码中的 9,000 可配置上限也是应用选择。界面必须区分三者，不将应用保护线说成 Cloudflare 限额。本方案当前不改变已授权的 8,000 配置；是否利用更多免费额度与计量修复分别决定。

15:37 只读生产仍为 7,992 / 8,000，666 条任务的暂停原因全部是本地 `daily-budget`。当前两个模型费率与官方一致。新复现还确认：每请求取整将 100 次各 100 token 的向量调用，从按费率合计 10.75 放大到本地记账 100；同样 input=100/output=10 的生成调用，成功时记 1，结果校验失败时保留 122。

昨日虚构样本真实联调中，向量调用成功但适配器记录的 usage 为零，不能据此认为免费，也不能在缺少原始响应时断言供应商没有返回字段。现有普通整数无法区分缺失和明确零。修复需要增加计量来源与字段存在性，并分别展示“已知用量折算 / 在途预留 / 未知用量保守估计”。供应商实际已用额度如未接入可验证读数，就显示未知或提供控制台入口，不把本地预留伪装成官方读数。

记账改用整数微单位（1 Neuron = 1,000,000 微单位），用 token × 对应每百万费率累计，只在展示时格式化；避免每个小请求都向上取成 1 Neuron。预留同样使用微单位，事务上限仍与日预算比较。

重新设计分模型预留：基于完整输入、模型模板和输出上限；向量请求不套用生成任务的大额固定余量。上线前用真实虚构样本、可验证 usage 或对应模型分词验证估计。若兼容接口持续缺少向量 usage，先验证可用的精确计量来源；没有证据时保留独立标识的估计，不能凭一个经验系数或将未知设零来降低占用。

截图与本地账本没有逐次、同时间窗口的明细对应，不能直接把约 6.3k 差额退款。Evan 随后明确授权一次性清账：先暂停 worker、导出旧账与时间基线并核验备份，再清空该 Cloudflare 账户的随机漫步预算账本，在修复版恢复前建立新比较周期。保留原文、向量、关系和处理进度；Cloudflare 的真实用量不会归零。新增精确流水不能伪造过去的实际用量。新的回归测试必须覆盖向量 usage 缺失、小请求累计精度与相同用量在成功/验证失败下结算一致。

### 5.2 持久化与结算

- `record_graph_source` 保存当前调度状态、阶段、阶段连续失败数、最后尝试/完成时间、next-attempt、状态版本和安全错误摘要。最近少量处理结果可用有界诊断结构保存，涵盖模型外的发布/存储失败。`updated_ts` 在每次有效状态变更时更新。旧 `attempts` 不能迁移成真实模型失败数。
- 扩展现有 owner / 预算元数据保存连接阻断、账号额度或服务冷却及恢复时间；同账号共享限制，不因多个 owner 或重启失效。不能把这些运行状态写进 `wander-config` 反复触发全库重算。
- 新增小型 `record_graph_call` 调用流水：每次外部调用一个唯一 ID，记录 owner、来源及版本、阶段、预算所属日、预留量、用量是否已知、结算量、开始/结束时间与安全错误字段；对同一调用最多结算一次。它同时为“处理详情”提供调用证据。
- 日志每次失败输出白名单结构字段；正常暂停记录状态变化即可，不每 5 秒刷一遍。页面不依赖容器日志存活。日志和诊断 API 不包含正文、模型原始输出或凭据。

预算顺序：在事务中预留并创建调用记录 → 发出请求 → 提取可验证的 usage → 独立进行内容校验 → 原子结算与保存结果状态。

1. usage 明确且有效时，即使输出校验失败，也按用量结算并退回过量预留。
2. 缺失 usage、请求结果丢失或进程中断时，保留保守预留。明确的 0 与字段缺失区分，不能用 `> 0` 代表“已知”。
3. 结算只更改该调用原先占用的账户/日期，跨 UTC 午夜仍结算原预算日；迟到响应不可归入新日。
4. 结算写入与预算调整保持同一事务，防止重复退款；失败可重放同一 call ID。无法确认已发送与否的调用不自动退款。
5. 若可靠用量高于预留，记录真实占用并暂停进一步请求，显式报告预留估算异常，不能把数值截断来掩盖超额。应用预算是保护阈值，不把估算说成供应商账单保证。

调用详情建议保留最近 30 天，每个 owner 最多 5,000 条已终结记录；当前预算日和待结算记录不参与清理，日聚合不随明细清理被回退。删除原文或用户时移除关联内容标识和可读诊断，已发生的预算计数保留。新表、字段、索引与触发器需要覆盖 SQLite、MySQL、PostgreSQL，并保持增量迁移与 `LATEST.sql` 一致。

## 6. 查询与重试接口草案

沿用受认证的 `/api/v1/journal/wander` 路由，不开放匿名诊断接口，不改变现行登录或 Token 权限契约。

| 接口 | 作用 |
| --- | --- |
| `GET /status` | 增量返回控制状态、互斥 progress、阻断原因、预算口径、恢复时间与 asOf；保留旧字段 |
| `GET /jobs?state=…&cursor=…&limit=…` | owner 限定的索引分页，默认 20、最多 50；摘要只读取当前页原文，不读取向量或全库正文 |
| `GET /jobs/{memoUID}/attempts` | 当前可读来源的有界安全诊断；历史不足明确说明，不补造旧时间或原因 |
| `POST /retry` | 单条或 `attention` 范围重排；仅返回排队回执，不在 HTTP 请求内调用模型 |

重试必须满足：仍是本人当前可处理的记录、自动处理仍启用、状态允许重试、revision 和状态版本未被替换。它不清空有效表示、不改原文、不调用 Configure、不推进全库重建。可对预算暂停期的 attention 项安排后续执行；已经等额度或排队的项不重复加入。

单条请求携带期望状态版本；批量请求在服务端形成明确、受限的目标快照，分批处理并返回进度。用 owner + request ID 保存幂等回执（可复用不触发图谱重建的 journal document 类型）；重复点击、响应丢失、跨标签页重试不产生第二次重排。用户点“重新安排这 N 篇”针对点击时的异常集合，不把过程中新增失败或正常项扩进去。

所有读写重新核验资格与所有权。API 不接受客户端 owner ID 决定作用域，不允许受限只读 Agent 凭据写入。清理失效项与列表分页使用稳定排序；统计在同一快照内一致，列表跨页发生状态变化可以返回刷新标识。

读路径不加载语义索引、不调用模型、不使用 worker 互斥锁。状态和列表查询限定元数据与当前页，避免后台长请求拖住阅读。重试只使状态查询失效；有新有效关系时沿用既有图谱更新路径，不因为进度变动重置阅读会话。

## 7. 已有失败任务怎样恢复

不把 17 写死在程序中。发布时重新读取符合条件的历史失败集合，以当时实际数量为准。

1. 先部署正确分类、预算和检查点逻辑，记录旧失败项数量及派生状态。保留生产发布流程的备份与回退证据。
2. 迁移后将旧 `invalid-result` 记为“历史原因未记录”。旧 `attempts` 仅保留为旧版领取次数，不作为新重试阈值；不存在的最后尝试时间保持未知。
3. 对仍已授权启用、当前资格有效、旧失败状态仍匹配的来源执行一次可重复安全的恢复。使用恢复版本标记，重启或重复运行不会再次重排。已删除、排除、归属变化和明确配置失败分别处理。
4. 保留匹配版本/profile 的有效向量与关注点，重排失败阶段；预算不足则显示已安排且等待恢复。按本次明确授权执行一次可恢复的旧账清理；此动作不是日常自动恢复策略，重启、重试不能反复清账。不得提高每日预算或重存全库配置来恢复。
5. 首批少量真实任务观察后，再让同一正常队列继续处理剩余项；校验调用记录、结算、关系双侧引文和状态反馈。真实校验再次失败可进入明确的有限恢复流程，不承诺所有历史项必然成功。

本次设计不变更模型、提示词或向量表示协议，因此不应仅因重试实现变化提升语义 profile 并重算已完成记录。关系发布检查点若需加格式版本，应与语义模型版本区分。旧代码不理解新状态和结算协议，回退必须通过受控发布暂停 worker、保留数据库与预算记录，不假定仅替换镜像即可安全恢复旧调度。

## 8. 验证与交付顺序

### 后端回归

- 把已复现的 4 项缺陷变成期望正确行为的正式回归测试：错误保真；预算等待不计失败；7992/8000 但不足单次请求正确展示等待；已知 usage 的失败结果仍正确结算。
- 网络错误不永久搁置；结构/引文失败达到有限次数后停止；服务恢复、进程重启、租约过期和无进展保护使用可控时钟验证。
- 重试保留有效阶段；发布重试不重复请求模型；空关系是成功；历史未知原因不伪造；恢复迁移重复执行不重复重排。

### 浏览器与体验

保持现有 A+C 的滚动位置和展开提示；面板开关、轮询、重试回执不重抽原文；查询失败也能继续读已有内容。按原 issue 的性能基线记录环境、样本数及 p95，后台模型长请求不能拖慢阅读 API。界面没有实现前不宣称“瞬间打开”已验证；此前冷启动性能缺口也不因此自动关闭。
