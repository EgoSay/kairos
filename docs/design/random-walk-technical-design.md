# 随机漫步：技术设计

Status: In progress — 技术方案 v0.2，2026-10-27；Cloudflare Workers AI 方案已确认，进入开发及本地验收，尚未实现。跟踪：[Issue #38](https://github.com/EgoSay/kairos/issues/38)。

前置产品方案：[随机漫步：沿着记录发现关联](random-walk-associations.md)，Evan 已确认 v0.2，要求继续讨论技术实现。本稿落实自动关联、语义检索、后台更新和即时阅读；不改变已确认的产品流程。

推荐采用现有 Go 进程内的受控后台任务、现有数据库中的派生索引与关联表、按账户隔离的内存检索、提前发布的局部阅读结果，以及前端有界预取。模型通过独立的 provider 调用；用户点开漫步不触发模型推理或向量检索。

## 1. 已核验的基础与新增能力

源码基线：2026-10-27，本地 HEAD 987990569；没有据此推断生产配置、硬件或记录数量。

| 现有能力 | 可复用部分 | 必须补足 |
| --- | --- | --- |
| Go 服务与 React SPA，数据库支持 SQLite／MySQL／PostgreSQL | 部署形态、认证、原文存储与阅读 | 语义整理、索引与局部结果读取 |
| useJournalCandidates 分页遍历全库后抽样 | 既有来源资格规则 | 替换漫步的全库前端读取链路 |
| MemoMutation 支持原文、引用和 journal 文档同事务提交 | 原子提交与版本检查模式 | 各种原记录变更入口的可靠任务登记 |
| partition 保存意图与租约任务 | 崩溃恢复、幂等和租约的本地模式 | 独立的图谱任务；不复用分区外发队列及其权限语义 |
| SSE 广播 memo.changed／space.changed，不携带记录信息 | 连接、多标签页协调、重连机制 | 图谱更新通知、版本核对、敏感缓存移除 |
| React Query 管理服务端数据 | 有界缓存与后台预取 | 账户、来源版本、图谱版本组成的缓存身份 |
| AI 洞察仅接受手选来源的聊天生成 | 已有服务配置管理方式、HTTP 调用约束 | 独立的 embedding 和关联分析能力 |

现有 SSE 的失效处理主要覆盖 memo、附件和统计；不能假设新漫步缓存已经接入。invalidateQueries 会保留旧数据供后续刷新，来源撤回时还需要主动清除相关内容。

## 2. 两条互不等待的链路

    记录提交
       ↓ 同事务登记变更
    持久任务 → 分段与原文定位 → 语义表示 → 多路召回
       → 原文核验与关联判断 → 更新主题和边 → 发布局部阅读结果

    用户点击
       ↓
    有效的前端缓存
       或：有界读取接口 → 来源有效性核对 → 已发布的局部结果
       ↓
    显示原文、附近节点、短提示与已经准备好的证据

关键约束：

- 阅读链路不调用 embedding、重排模型、聊天模型或全库聚类。
- 原文提交不等待推理；任务登记很小，模型调用在数据库事务外。
- 后台更新与已发布结果并存。新版本完整可读后切换，单条记录变化不让全库重新进入准备状态。
- 外部服务故障主要影响新关联的新鲜度；原文与仍有效的已有图谱可继续阅读。
- 单机初版无需 Redis、消息中间件或图数据库。扩容由测量触发，公开读接口不随检索实现改变。

## 3. 语义理解：同时保留原文与问题视角

### 3.1 原文分段

短记录保留为一个完整片段。长记录沿 Markdown 段落、句子与标题分段，初始实验预算约 300–800 个汉字，另按实际模型 tokenizer 检查硬上限；不能把字符数当 token 数。相邻片段可保留一到两句上下文，按来源去重。

每个片段保存 memo UID、正文哈希、片段顺序、原文 UTF-8 字节区间和提取版本。语义检索使用的纯文本与原文区间有映射。用于证据的引文必须来自原始正文，不能把清理后的文本、生成标题或摘要冒充原话。

长记录不能只做一条整篇向量，否则一个局部思考容易被其它内容淹没。不同片段命中最终归并到原记录，长文不会因片段多而占满结果。

### 3.2 两种可检索表示

| 表示 | 输入 | 目的 |
| --- | --- | --- |
| 原文表示 | 短记录或长记录的语义片段 | 找到意思相近、同一事件或同一具体问题的内容 |
| 问题表示 | 从原文提取、带引用的一到三个具体关注点；允许为零 | 跨越爱情、家人、工作等表面话题 |

虚构例子：

- “希望伴侣明白，但我又没说”支持“期待对方理解未表达的需要”。
- “没告诉父母，怕他们担心”支持“表达需要与不让家人担心之间的顾虑”。
- 两条问题表示可以帮助召回彼此，但是否连线仍由双方原文决定。

关注点提取输出结构化内容：具体问题、支持它的原文区间、原文中明确的场景与立场。未明说的主体、情绪和原因允许为空；不生成固定人格、心理病因或未经证实的实体合并。

问题表示是检索辅助，不能作为下一轮新证据引用。任何最终连接必须落到原记录，不允许“AI 的猜测支持另一个 AI 的猜测”。

### 3.3 模型建议

2026-10-27 实施决定：使用 Cloudflare Workers AI 托管的 `@cf/qwen/qwen3-embedding-0.6b` 和 `@cf/qwen/qwen3-30b-a3b-fp8`，通过后端直接调用 API。已有的是服务接入代码，不能假设实例已经配置任何模型。账户 ID、凭据、计划和真实请求均须在联调时验证；先使用虚构中文记录，不自动处理生产私人记录。

Workers Free 当前每天有合计 10,000 Neurons 的免费额度，额度耗尽后请求失败，UTC 00:00 重置。任务持久暂停并跨日续跑，优先新增/修改，历史回填允许跨日。预算按整个账户共享计算，模型输出和重试也计入；不自动升级、切换付费模型或付费服务。若账户已在 Paid 计划，超额会计费，应用预算不是平台账单的绝对硬上限，必须先核对账户计划。

服务配置和使用说明明确：相关原文会发给 Cloudflare 推理，图谱与向量保存在 Kairos 数据库。Cloudflare 声明不将 Workers AI 客户内容用于训练；标准无状态请求、网关日志/缓存及异步批处理的数据保留条款不同。首版使用普通无状态推理，不新增内容日志或网关缓存。

- 嵌入模型先验证 Qwen3-Embedding-0.6B、1024 维。理由是支持中文所在的多语言场景、任务指令和较小模型规模，便于比较服务化与自托管路径。官方模型卡确认维度与能力范围，不证明它已适合 Kairos 的记录。
- 同系列更大嵌入模型仅保留为未来质量对照；本次默认使用 Cloudflare 已托管的 0.6B，不引入额外服务。不同模型输出不混用。
- 关注点提取、关系判断与命名使用上述 Qwen3 生成模型，复用已有服务配置方式并增加独立任务提示和输出校验；真实质量和服务能力由联调验证。
- 独立 reranker 暂作为评估项。先让有限候选直接接受带证据的结构化关系判断；只有能明显减少后续模型消耗或改善排序时，才增加 Qwen3-Reranker 等常驻依赖。

向量在保存前检查数量、响应对应关系、维度、有限数值与非零范数，统一 L2 归一化。记录 model、revision、dimension、输入角色与指令版本；不能直接比较不同配置的向量。

记录之间的相似度采用一致的文档表示；以“具体问题”检索原文时使用对应的 query 指令和文档表示。两种召回各自排序后融合，不混合未校准的原始分数。模型升级或指令变化建立新索引版本，准备好后切换。

## 4. 检索：先尽量找到，再决定哪些值得读

每个新／变更节点的初始候选预算如下，均为可调实验参数：

1. 原文语义召回：取前 40 个候选片段，归并原记录。
2. 关注点召回：每个关注点取前 20 个候选，帮助发现跨主题连接。
3. 字面与已有结构：中文字符片段、英文词、明确标签及本人已有引用补充候选；这些信号不直接证明语义关系。
4. 合并去重，先排除本人已否定、来源无效和不具资格的内容，总候选上限初设 60 条。
5. 用各路名次融合，避免把余弦分数、字面分数和手动引用强行相加；再按重复程度、时间与问题多样性选出最多 12 条供深入判断。

字面召回可先使用 Go 中可重建的有界倒排索引，中文以字符片段提供基本匹配，英文按词切分。先验证在真实中文短文上的补充价值，不为了“混合检索”默认引入另一套搜索服务。本人标签只是信号之一，无标签记录具有同等来源资格。

当前任务中的“检索”首先服务后台建图与从某条记录出发。以后自然语言搜索可以复用同一索引，但自由输入的新问题需要在线生成查询向量，不能承诺与已预取的漫步拥有相同的 100 ms 延迟。本轮不顺带改造顶部搜索界面。

## 5. 从候选到可信的关联

### 5.1 关系判定

给模型的输入是有界的双方原文及必要上下文，要求输出：

- 是否值得并读；可以明确返回无合适关系。
- 关系类型：同一问题、补充视角、不同说法、跨场景联系。
- 双方支持这条关系的准确引文与片段标识。
- 一句简短提示，以及必要的语境差别。

结构化校验包括来源白名单、片段归属、引文逐字匹配、来源版本和字段长度。模型生成的 ID 或引用不能指向未提供的材料。引文匹配只是必要条件，不能证明解释成立；还需用质量样本评估是否曲解语境。

模型只接收阅读材料和固定分析任务，不获得工具、数据库写入或外链抓取能力。笔记中出现的指令按内容处理；结构化输出不能直接变成执行指令。

初期每个节点保留一小组通过核验的边，首屏挑两到四个方向。没有证据就少显示；重排不以“意外程度”压过关联可信度，也不把模型自评分当成概率。

### 5.2 图谱的实际结构

图谱主要有原记录与主题／问题两类节点：

- 记录—记录：保存关系类型、两端原文依据、来源版本、生成配置与否定状态。
- 记录—主题：保存这条原文怎样支持这个主题；允许多重归属。
- 本人手动关系：保留现有来源和语义，展示时与系统建议区分。

主题生成先从带证据的关注点出发。将新关注点与已有主题的代表关注点检索匹配；模型依据代表原文确认是不是同一个具体问题。不能匹配时保留为候选，得到多条独立记录支持后再成为主题节点。

主题命名引用支持材料；相同主题的合并、拆分在后台低频进行，并尽量保留稳定 ID。仅靠向量连通分量容易把多个主题经泛化词串成一个大团，因此主题必须检查代表材料、内部差异与名称具体程度。

共享一个主题不意味着主题内任意两条记录都已形成直接关系。A 与 B、B 与 C 有边，也不自动宣布 A 与 C 有边。漫步呈现实际核验过的连接。

### 5.3 起点与路径

按时间和主题适度分层选择起点，并保留孤立节点被遇见的机会。降低近期重复的权重；不把连接度或停留时长作为主要抽样权重。

当前步的候选根据可信度、具体性和多样性选择；明确相反的观点也可能值得并读。近似重复仅降低同屏拥挤，不删除原记录，也不把重复思考视为无价值。

换起点是新的随机跳转，界面明确区分于沿边继续。路径只保存用户实际走过的状态。

## 6. 存储与检索实现的推荐

### 6.1 现有数据库保存事实和可重建结果

新增专用、按 owner 隔离的派生表，具体表名在实施时确定：

| 数据 | 主要字段与索引 |
| --- | --- |
| 来源索引状态 | owner、memo UID、文本哈希、来源资格代次、待处理／已处理版本 |
| 片段与表示 | source version、span、表示类型、model profile、vector BLOB |
| 建议边 | owner、两端 UID、类型、证据区间、两端版本、生成版本、可读状态；两端均有邻接索引 |
| 主题与成员 | 稳定主题 ID、名称、代表来源、成员依据与版本 |
| 局部阅读结果 | owner、node、邻域版本、节点／边 ID 与布局顺序；不复制全库正文 |
| 持久任务 | owner、对象、阶段、目标版本、状态、租约、重试时间；按到期任务索引取有限批 |

设置、否定反馈和索引版本元数据可沿用 journal 文档模式。向量和频繁邻接查询使用专用表，避免把整个图谱写成一个巨大 JSON 文档。

SQLite、MySQL、PostgreSQL 同步增加迁移与 LATEST.sql。原文仍在 memo，已有手动关系仍在原表。新图谱是派生数据，单独清理不会删除原文；反馈等用户意图与派生索引分开保存。

备份恢复保留用户反馈与服务配置状态，索引可重建。恢复后先重建资格代次、校验来源，再开放派生结果；不得借旧任务直接向外部服务重放。恢复流程应遵循已配置的自动处理策略并明确显示服务状态。

### 6.2 首版在 Go 内做精确向量检索

按账户加载归一化 float32 向量块，使用点积加有界 Top-K；持久版本保存在数据库，内存仅为可重建索引。后台任务与将来的语义搜索读取它，漫步接口不经过它。

1024 维的一万个向量约为 39 MiB，三万个约 117 MiB；这只是向量本体，不包括原文、对象、倒排索引、缓存和更新期间的峰值。记录数不能直接当作向量数：长文分段、关注点表示都会增加数量。

索引采用分块更新与版本切换，避免每改一条复制完整账户索引；多账户按预算加载，设置总内存、并发与空闲回收限制。启动时先提供持久化的局部阅读结果，索引加载不阻断漫步。

评估扩容的触发条件：目标机器上检索 p95 超过分配预算（初设 100 ms）、索引常驻内存超过可用预算，或回填吞吐无法达到约定的新鲜度。届时优先评估 Qdrant 的向量索引，替换召回实现，图谱证据、读取协议与 UI 无需重做。HNSW 的内部搜索图不是用户看到的语义关系图，两者独立。

### 6.3 本轮合成基准

2026-10-27，当前开发机，Go 1.24.3 darwin/amd64；宿主 uname 为 arm64，不能作为生产 linux/amd64 或项目 Go 1.27 的性能结果。单线程标量点积，1024 维归一化随机 float32，Top-40 最小堆；每组预热 8 次、计时 50 次。

| 向量数 | 向量本体 | p50 | p95 |
| --- | --- | --- | --- |
| 1,000 | 3.91 MiB | 0.67 ms | 0.78 ms |
| 10,000 | 39.06 MiB | 6.60 ms | 7.00 ms |
| 30,000 | 117.19 MiB | 20.21 ms | 20.81 ms |

实验只测内存扫描与 Top-K，不含 embedding、数据库、资格过滤、并发、网络、图谱或浏览器。它支持“先验证轻量精确检索”的工程选择，不证明端到端速度、关联质量或全库回填耗时。全库初始化仍存在累计扫描成本，必须分批、限速并测总耗时。

以上表格保留开发阶段的临时实验观察，不把该实验当作产品模块或正式性能验收。

## 7. 可靠增量处理

### 7.1 不丢变更

原文写入与待处理意图同事务提交，即使响应丢失或进程随即退出，也能恢复任务。任务仅记录对象与目标版本，工作时读取当前原文。

需要覆盖普通创建／编辑、导入、恢复、归档、删除、归属变化，以及回顾排除设置和手动关系的变更。不能只挂在前端保存按钮或某一个 HTTP handler 后面。

沿用现有事务模式，但不直接假设 MemoMutation.JournalDocuments 能覆盖所有场景：当前它要求本人写入，管理操作与其它存储入口必须分别覆盖。语义变更登记应在相应的存储事务内完成，由 core 层决定处理策略。

### 7.2 合并、领取和发布

- 任务按 owner／memo／阶段合并，短时间连续编辑只处理最新目标版本。
- 有限 worker 以版本比较领取租约；超时可重领。每阶段结果以来源版本和模型配置为幂等键。
- 每次外部调用前检查当前来源资格和配置代次；完成后再次检查，再发布。旧响应不能覆盖新版本或恢复已撤回的来源。
- 不承诺外部模型请求严格一次：响应丢失可能导致重复计费。可用稳定请求 ID 时使用，并记录尝试次数与消耗。
- 先处理新增和修改、已就绪区域的补齐，再处理历史回填。为回填保留最低进度，避免长期饥饿。
- 根据实际服务限流和 Retry-After 退避；不可重试错误停止该阶段。配置每批 token／字节、并发和预算上限。
- 初始任务登记失败不能静默丢失；同事务整体失败会按保存错误报告。正常推理失败则仅影响后台进度。

首次回填以稳定游标分页，配合变更水位和轻量对账，覆盖扫描期间的新增与修改。对账比较版本，不是周期性把所有正文重新送给模型。

### 7.3 保护保存与阅读

现有 SQLite 已开启 WAL，但仍需要控制写事务长度。网络调用、模型推理、全库扫描不持有写锁；派生数据分小批提交。后台使用独立并发预算与低优先级调度，测量写入延迟回退。

文本没变时复用向量；日期或引用变化只更新受影响的关系与展示；纯布局调整不重新嵌入。反馈变化只重排对应区域。索引维度／模型改变走完整新代次，不能把两套向量混在一起检索。

## 8. 漫步读取接口与版本约定

先沿用现有 /api/v1/journal 私密 JSON 路由，使用现有认证规则，不新增公共入口或改变凭据能力。下列为拟定协议：

| 操作 | 返回／作用 |
| --- | --- |
| POST /wander/bootstrap | 随机起点与局部结果，可带少量本次已看 ID；不创建模型任务 |
| POST /wander/neighborhoods | 最多 4 个指定节点的局部结果，供切换与预取；返回经过资格校验的结果 |
| POST /wander/validate | 有界校验当前持有的节点／来源版本；在失效通知或重连后使用 |
| POST /wander/feedback | 否定或撤销一条建议；幂等，绑定 owner、记录对与关系类型 |
| GET /wander/status | 索引可用性、更新进度、失败原因、最新资格与图谱版本 |

响应包括 owner 上下文、索引配置代次、局部版本、来源版本、原文片段、已准备的证据、候选方向和预取节点。以逻辑对象描述协议，实施前再定完整 schema；不手改生成 proto。

服务端使用邻接索引查询有限节点，批量读取原文并核对资格和版本，避免每条边一个数据库请求。原文片段按字节预算返回；证据文字由服务端按已校验区间提取，前端不拿 UTF-8 字节偏移直接切 JavaScript 字符串。

局部结果的发布是原子的：边、证据与来源绑定完备才 ready。主题名称同时绑定其支持来源；某个来源撤回时，依赖它的标题也必须失效。

可沿着继续的节点必须已有可读邻域，不能只准备一张候选卡片、点击后才开始为它找关联。新边发布时更新两端邻域，先形成有限的可读区域；这不要求递归准备无限多步。回填期间只开放已准备的路线，区域边缘如实显示当前没有更多已就绪方向。

主题名称使用有界的代表来源作为依据，并记录依赖；读取一片地图不扫描整个主题的所有成员。首屏限制节点、边、代表来源与总字节数，主题成员总数和完整列表另外分页读取。

索引配置代次、局部内容版本与来源资格版本分别处理：普通后台新增关系不驱逐用户正在读的原文；来源撤回立即使相关缓存不可用。

## 9. 前端如何把等待提前

### 9.1 三段准备

1. 主应用已经可记录后，低优先级预取漫步路由资源和 bootstrap。入口聚焦／指针靠近时提升优先级；手机不依赖悬停。
2. 首屏进入时，一组结果已经包含当前原文、邻近片段及展开依据，消除串行请求。
3. 当前节点显示后，只预取直接相邻的两到四片与少量备用起点。先准备文本，不抢下载大图或原音。

客户端用现有 React Query 管理数据，组件只保存焦点、路径、滚动与展开状态。预取与实际读取共享同一 key；key 包含账户、索引代次与节点身份。配置一致的有效期，避免预取刚完成、挂载就立即重取。

版本机制判断内容能否使用，时间 TTL 只负责容量和补充核对。首轮建议会话缓存最多 20 个局部结果或 5 MiB 文本，先到上限先回收；实际堆占用另测，不能用 JSON 字节数等同浏览器内存。

### 9.2 点击与渲染

- 点击相邻节点时，从有效缓存立即切换原文；附加内容在当前位置补充，不全页闪白。
- 依据展开只改变局部状态。源片段、提示与证据共用数据，不重复生成。
- 原文与地图拆分渲染；地图更新不重建整个 Markdown 阅读树。大型 Markdown 扩展、媒体和复杂图形按需加载。
- 首版局部图用普通 DOM 节点和 SVG 连线，固定分区／层级槽位；保持来路位置。单次仅显示有限节点，避免依赖持续运行的力导向布局。
- 路径状态引用缓存对象，不反复复制全文；长文展开按需读取并恢复滚动。
- 请求携带 AbortSignal；可取消的过时预取及时取消。焦点另由操作序号控制，已完成但迟到的响应只能填缓存，不能把画面切回。
- 图片预留尺寸，正文尽早用可用字体显示；字体加载不得遮住原文。减少动态效果时直接切换。

### 9.3 缓存有效性

现有 SSE hub 是全局无主体广播。若新增 journal.graph.changed，首版继续仅携带事件类型；不能直接在公共广播中加入 owner、memo UID、主题或正文。收到事件后，只对当前账户做有界版本核对，并合并短时间重复请求。

memo.changed／space.changed、恢复可见、重连或账户变化会触发资格核对。确认撤回时立即移除正文、提示、主题和相关局部缓存；仅标记 stale 并后台刷新不够。

断联后不继续将未校验的缓存当作最新授权结果。当前已显示文字不能被远程瞬间抹除，这个物理边界需要保留；重新连接后先校验再继续新遍历。热缓存 100 ms 目标以会话有效且版本已核对为前提。

## 10. 模块落点

| 位置 | 职责 |
| --- | --- |
| core/recordgraph/（新增） | 图谱构建、关联规则、检索组合、任务处理、局部结果发布与读取；把复杂性集中在一个有清晰输入输出的 Module |
| provider/ai/embedding/（新增） | 文档／问题向量的 HTTP Adapter、配置能力校验、响应检查 |
| provider/ai/association/（新增） | 关注点与关系的结构化模型调用；不直接查库或保存图谱 |
| store/ 与三个数据库 driver | 原子变更登记、任务租约、版本和派生数据持久化；不写提示词或做模型判断 |
| server/api/v1/ | 薄路由、账户上下文、请求上限、错误映射与无内容 SSE 通知 |
| web/src/hooks/ 与漫步组件 | 查询／预取，局部阅读状态、地图与既有原位阅读复用 |

core 对前台提供少量稳定操作：获取起点、获取邻域、校验版本、反馈与状态。检索和模型步骤不拆成前端需要串行调用的一组接口。

不提前建立通用 AI 编排框架。模型连接确实可变，因此有 provider seam；检索更换也限制在 recordgraph 内部。当前只有一个消费者的局部逻辑留在模块内，避免为了将来扩展增加透传层。

## 11. 性能、质量与成本怎么验收

### 11.1 产品延迟

沿用产品稿目标：有效预取下进入／切换／返回／展开 p95 ≤ 100 ms；已准备但浏览器缓存未命中 p95 ≤ 800 ms；冷启动直达首屏 p95 ≤ 1.5 s。800 ms 与 1.5 s 的参考条件为 RTT 100 ms、下行 10 Mbps、中档手机，原文先可读，媒体另计。

后端有界读取 p95 ≤ 100 ms，首屏压缩数据 ≤ 100 KB。后台正常无积压时增量新鲜度 p95 ≤ 2 min；首轮回填独立报告，不伪装成增量更新。

分别记录点击到原文首帧、邻近节点可操作、缓存命中率、长任务与帧时间、服务端权限与查询耗时。目标环境采用项目工具链与生产等价资源，报告样本数、p50／p95、错误率。本轮合成基准不能替代这些数据。

### 11.2 关联质量

先建立受控中文样本，包含无标签、同义表达、同词不同义、不同主体、相反观点、跨场景共同问题、重复思考、短句、长文及真正无关系的内容。生成／调参材料与评估材料分开。

| 层次 | 评估什么 |
| --- | --- |
| 召回 | 人工标注的合理连接能否进入候选；分别看同主题和跨主题 Recall@K |
| 关系判断 | 可读候选中有多少被认为值得并读；哪些解释牵强或漏掉语境 |
| 原文依据 | 引文逐字对应、出处和版本正确；零越权来源 |
| 展示 | 最前几条是否重复、单一、难以理解；无可信联系时能否正确少显示 |
| 本人体验 | 是否发现未注意的联系，提示有没有抢走自行理解空间 |

模型规模、候选预算、是否增加 reranker、阈值和主题合并规则由这些结果裁决。不能用一个通用向量排行榜或模型自评分宣布达到“有意义”。

### 11.3 可靠性与成本

必须验证任务崩溃恢复、并发编辑、删除发生在模型请求途中、旧响应晚到、租约重领、多账户隔离、导入期间对账、模型版本迁移、缓存撤回与 SSE 漏事件后的恢复。

记录每千条文本的嵌入 token、关注点与判边调用数、重试消耗、回填耗时、派生空间和实际费用。成本近似为“片段嵌入 + 每条有限关注点提取 + 每条有限候选判断”，不对所有记录两两调用大模型。未核对服务价目与文本分布前不报虚假总价。

## 12. 推荐实施顺序

| 阶段 | 交付 | 进入下一步的证据 |
| --- | --- | --- |
| 1. 语义与性能验证 | 受控样本、模型端点能力、召回／判边对照、目标机器读写与检索基准 | 证明跨主题联系可被找到且有依据，选定服务和资源预算 |
| 2. 后台与版本闭环 | 原子任务、增量索引、关系和证据、局部结果、撤回与恢复 | 来源变更与故障测试通过，可稳定发布并读取结果 |
| 3. 连续阅读界面 | 直接进入、预取、单击切换、原位依据、返回、手机局部图 | 冷／热性能及键盘、手机、快速操作和失败流程通过 |
| 4. 获准样本体验与发布准备 | 真实关联评价、监控与费用记录、迁移／备份核验 | 工程与本人体验分别达到目标；发布另按仓库流程 |

第一阶段只做有界验证，不先实现完整地图再期待后端产生有意义的关系。后续可以增加更大模型、独立向量索引或专题视图，核心读取协议和来源规则保持稳定。
